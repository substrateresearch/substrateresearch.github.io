Publications · A research presentation — ACCL

What ran, where it ran, and whether it was what was asked.

ACCL — Auditable Computing and Contractual Execution · 24 November 2026. An experimental execution-verification system designed to establish what ran, where it ran, and whether its execution satisfied a declared contract.

1. The problem

Most computing systems tell you that an operation succeeded. That sentence is a claim, made by the system that ran the operation, about itself. Ordinarily it is believed, because ordinarily there is no alternative on offer: the log says what the program printed, the receipt says what the executor recorded, and checking any of it means trusting the same party that produced it.

That arrangement is becoming load-bearing in places it cannot carry. Autonomous systems now execute work whose details no human reviews — choosing machines, precisions, and data paths as they go. When such a system reports success, the questions that matter are not answered by the report:

Can an independent party establish what an autonomous system was instructed to execute, what actually executed, where it executed, and whether the result satisfied the original contract?

ACCL exists to answer that question — not with a stronger assertion, but with evidence an independent party can check without adopting the Institute’s word, or its philosophy. The central proposition: intelligent systems must be accountable for their execution, not merely for their outputs.

One distinction governs everything that follows, and it is the scientific core of the work: a receipt generated by the executing machine is not automatically proof of physical execution. A record can establish that a computation’s result is correct, that a file has not changed, that a claimed path survived controls designed to catch substitution — each a different strength of evidence, and none of them interchangeable with the others. ACCL’s contribution is to make those strengths explicit, graded, and checkable, rather than letting a single word — “succeeded” — stand for all of them.

2. The architecture

Five components, each with one responsibility:

ComponentResponsibility
Execution contractDefines what is permitted and expected
Execution identityIdentifies the software, hardware, runtime and artifacts
Execution receiptRecords what happened
Independent verifierChecks the receipt against the original contract
Arbitration recordDocuments disagreements, failures and unresolved claims

The contract is fixed, and its hash computed, before any execution it governs. A contract assembled after the fact can describe anything; the ordering is the discipline. A contract also declares its evidence requirement — the minimum class of evidence a receipt for it must reach. A contract that asks for no evidence gets a receipt that establishes little, and the receipt will say so.

Evidence classes

Receipts claim a class. Classes have satisfaction rules, a verdict always states the class it reached, and a receipt’s class is set by its weakest supporting element.

  • Self-reported (E0). The executor’s own record, bound by content hashes. Establishes that the record existed in this form when hashed and has not changed since. Does not establish that the execution happened, happened where claimed, or produced the recorded output.
  • Cross-checked (E1). The result was independently recomputed by a second implementation that shares no code with the executed one, and compared within the contract’s tolerance. Establishes that the recorded output is the output the contracted computation produces, whoever ran it. Does not establish where the original ran.
  • Corroborated (E2). The execution was surrounded by controls designed to catch substitution, silent fallback, and environment lies: pre-registered environment checks, introspection of the operative execution path, paired negative controls whose failure is expected if the claimed path is real, structural integrity checks over protected artifacts. Establishes that the claimed path was the operative one, to the strength of the controls actually run — which the receipt must enumerate, because E2 without an enumeration is a slogan.
  • Hardware-attested (E3). A hardware root of trust signs measurements of the executing code and device state, and the verifier checks the signature against the manufacturer’s chain. The strongest binding available between a receipt and a physical execution. In v0.1 it is defined, and not instantiable: no ACCL backend produces attestation today, and a v0.1 receipt must not claim it.

Three design decisions

The verification architecture rests on three decisions, locked before the final implementation was built:

  1. Independent computation. The verifier implements the operation itself. Schemas, canonicalisation, and cryptographic primitives may be shared; the arithmetic being tested may not. A defect in a shared implementation would pass both sides silently.
  2. Overflow rejected. Strict signed-integer semantics: a contract whose inputs would overflow is invalid before execution. No silent wraparound; one unambiguous result per permitted input.
  3. Verdicts decoupled, acceptance fail-closed. Contract binding, computation, artifact integrity, and provenance are separate findings. An overall pass means the evidence package satisfies the implemented checks — not that physical execution was authenticated. Any axis failing fails the package; an axis that cannot be established where the table requires one fails it too.

3. The experimental evidence

The Execution Receipt Specification was frozen at v0.1 on 18 November 2026. The demonstration that accompanies it — Phase 7 in the public repository — is deliberately small: one operation (32-bit integer vector addition), three artifacts (a contract, a receipt, a verification report), and a verifier that works without trusting the executing program’s assertion that it succeeded. It is standard library only, and a stranger can run it in one command.

What the record shows:

  • The test suite. 23 tests pass on two different machines (the project VM and the Strix Halo): the verdict decision table, integer boundary conditions, overflow and malformed-input rejection, and the adversarial suite. Expected outputs in the independent vectors are written literally in the tests — computed by hand, not by the code under test.
  • Tampered output fails. Change the recorded result and the verifier’s own recomputation disagrees: computation FAIL, overall FAIL.
  • An altered artifact fails on its own axis. Bind the receipt to a program file, then alter the file: the mathematics still passes and the package still fails — computation PASS, artifact FAIL, overall FAIL. The axes borrow nothing from each other.
  • Forged hardware claims change nothing. Rewrite a receipt to claim hardware it never ran on and it verifies exactly as the honest one does, with provenance marked INDETERMINATE. A claim is not evidence, and the verifier never treats it as any.
  • History still verifies. A receipt produced by an earlier, superseded implementation — preserved untouched — verifies under the final verifier, and its tampered variants produce exactly the decision table’s verdicts.
  • Determinism across machines. The demonstration’s receipt and report files are byte-identical on both machines (SHA-256 a269cb9f… and 25d35ff1…), and the reference contract’s digest (7ccd837a…) is the same under all three implementations the work passed through.

The build history is part of the evidence, and is recorded in the repository. Three implementations were built in sequence, each answering defects in the last — including one defect found by audit, not by accident: an early verifier gave a mathematically correct output a computational FAIL when its bound artifact had been altered, coupling two verdicts that the architecture now keeps separate. The coupling was confirmed, decided against, and removed; the case that exposed it is in the test suite.

The patterns behind the classes predate the demonstration. Independent recomputation (E1) is the pattern of ACCL’s original proof harness — a float64 reference against the fp32 path, maximum absolute error 1.54e-06, zero disagreements over 1,000 seeded samples. Corroboration (E2) was established in practice on the NPU enablement track — the probe recording the active tensor class rather than accepting a success log, the paired control that failed without the runtime’s required conditions, a structural leak test leaving 32 protected files byte-identical. Phase 7 assembles those patterns into receipts; it does not exaggerate them.

One further run extends the record across architectures. On 22 November 2026 the unmodified demonstration package was run under a specification frozen before the run (ACCL-HET-01) on two machines that share almost nothing — the Strix Halo (x86-64, Python 3.14.4) and an NVIDIA AGX Orin (ARM64, Python 3.12.3), connected by a direct link. The test suite passed 23 of 23 on each machine. The receipts and verification reports produced on both were byte-identical to the reference anchors (a269cb9f… and 25d35ff1…). Each machine then verified the other’s receipt, and a third machine verified both: every axis passed, with provenance INDETERMINATE throughout. A tampered copy of the Orin receipt — one recorded output element changed — failed verification, as required. The pre-registered verdict was CORROBORATED-ACROSS-ARCHITECTURES: the same evidence, produced independently on dissimilar hardware, agreeing byte for byte. What the run establishes is that the record does not depend on the machine that produced it. What it does not establish is unchanged: where either execution physically ran remains INDETERMINATE, and no hardware attestation is claimed.

4. The remaining limitations

Stated at the size they actually are:

  • Below E3, a receipt is evidence, not proof. E0–E2 raise the cost of a false record and catch whole classes of accident and substitution. A determined executor who controls the machine and fabricates every artifact consistently defeats them. The specification does not claim otherwise.
  • Provenance is INDETERMINATE in every report the current system produces. Nothing yet establishes where an execution physically ran. Overall PASS must never be read as authentication of physical execution.
  • The strongest class cannot yet be produced. E3 is defined; whether the Strix’s firmware TPM can produce usable quotes is an open investigation, and datacenter attestation does not exist on this hardware.
  • Arbitration is specified, not implemented. The specification defines the arbitration record; the demonstration does not produce one. Disagreements are currently resolved by the decision table or not at all.
  • The demonstration is small. One operation, small vectors, one machine class, no signatures, no secure clock. Timestamps in receipts are claims; ordering is established by hash binding, not by clocks.
  • A verified verdict is narrow. It certifies that the contracted computation ran within its declared bounds. It does not certify that the model is good, the contract was wise, or the output should be acted on.

5. Run it yourself

The demonstration is public, in the phase7/ directory of the repository: github.com/salvajek356-sys/aacl/phase7

Run the verifier against the supplied contract and receipt and it passes. Then change something — the recorded output, the bound program file, the hardware the receipt claims — and run it again. The verdicts are the argument; the Institute would rather you tested them than believed this presentation.

The specification, the architecture decisions, and the full Phase 7 record are in the same repository, and the guide to the wider work is on the record at The compatibility layer.

6. What this is for

The definition the work supports, and does not exceed:

ACCL is an experimental system for independently evaluating whether computational results and supplied execution artifacts satisfy explicitly declared contracts, while distinguishing verified evidence from unsupported execution claims.

The open work, named in the specification itself: generalise the verifier beyond the demonstration operation; assemble corroboration into receipts as a matter of routine rather than occasion; implement the arbitration record; and settle whether hardware attestation is reachable on hardware like ours. Each will be reported the same way this was — the evidence first, the limits at full size, and the failures in the same register as the passes.
