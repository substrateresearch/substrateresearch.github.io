Publications · A reader’s guide — ACCL

The compatibility layer.

A reader’s guide to the Agentic Acceleration Compatibility Layer · 16 November 2026. What it is, how a request travels through it, and where it honestly stands — written to be read, not just audited.

The problem, in one story

Every program that runs a model wakes up on a different machine. One has a big graphics card and no memory to spare; the next is a modest laptop chip that sips power; a third is a server across the country that you’re not allowed to send your data to. Today, the program is expected to know all of this in advance — which hardware, which precision, which limits — and to be rewritten when any of it changes.

That is backwards. The program should be able to say what it needs — “this result, this fast, in this much memory, and my data stays on this machine” — and the machine should introduce itself honestly: what it can do, what it can’t, and what it has actually managed lately. Somewhere between the two, something has to make a decision it can explain.

That something is the Agentic Acceleration Compatibility Layer. AACL, or ACCL if you’re reading the older documents — the name wobbled before the idea did.

What it does with a request

A request arrives as a WorkloadSpec: the job, stated as requirements rather than instructions. Then, in order:

Discovery. The runtime asks each backend what it can genuinely do — architecture, precisions, memory, which operations really run — and writes it in a capability registry. Claims are recorded as claims.

Candidates. For each backend that might fit, the planner sketches a possible way to run the job: this chip, this precision, this artifact.

The gate. Candidates are filtered twice, and the order matters. First hard constraints — a plan that can’t fit in memory is not a plan. Then policy — a plan that would send local-only data to a remote machine is forbidden, and no score, however fast, is allowed to make a forbidden plan look attractive.

The choice. Survivors are scored by target pressure: how close each one comes to breaking the tightest promise the workload itself made. The winner comes with a sentence a person can read — “chosen because it sits at 62% of its latency budget” — not a number nobody can explain.

Execution, with a way back. If the chosen plan fails, the executor doesn’t improvise. The plan carries its ranked alternatives with it, each attempt re-passes the policy gate, and a backend that claimed it could do something it couldn’t gets its reliability marked down in the registry. Execution is the experiment; the registry keeps score.

Telemetry. Every run is recorded — what was asked, what was chosen, what happened, how long each part took. Not as a dashboard. As evidence.

And at the end of the road, when agents are the ones submitting work: a signed receipt for every execution, so an agent can prove to whoever trusted it exactly what ran, where, on what data, and why that plan — while never being able to override the rules itself. Trust without control. That phrase is the whole endgame.

Where it honestly stands

This is a young project, and this guide will not pretend otherwise.

On paper, it’s finished twice. A roadmap (From Concept to Working Runtime) lays out the build in milestones. A companion (Finishing the Thought Experiment) then argues with the roadmap — replaces its scoring math, its fallback story, its missing pieces — and extends it two milestones further. The argument is part of the record, on purpose.

In code, it’s a proof, deliberately tiny. The v0.1 proof runs the whole path — normalize, discover, plan, gate, execute, record, respond — for one small hand-built model on an ordinary CPU. Twelve tests, all passing, with the evidence saved. It proves the pipe, not performance: no graphics card, no real acceleration, no quantization yet. Its own README says so, in a section titled “What this proves (and does not).”

As of 16 November 2026, the proof has been moved, piece by piece, into the package layout the roadmap specifies — and the move was verified the only way that counts: the original tests, unmodified, still pass, and the proof’s measurements reproduce its September evidence to the last digit. That is Phase 0 of the build plan. The contracts grow teeth in Phase 1.

What it does not do, yet: run a real model, touch a GPU, quantize anything, or arbitrate between two agents who both want the same chip. What it will never do, by design: let the thing submitting the work decide whether the rules apply to it.

Try the proof yourself

Three commands, no downloads, nothing leaves your machine:

python3 -m venv .venv
.venv/bin/python prove.py

That runs the twelve tests and regenerates the evidence folder — the same numbers quoted above, produced on your hardware instead. If they don’t match, that’s a finding, and findings are the point.

Ask the API for the input [1,2,3,4] and you should get a score of 4.375 and label 1 — the reference result the tests check. Then try forbidding things: allow only int8 precision and watch the runtime refuse, in writing, rather than quietly doing something else. That refusal is the product, in miniature.

The road ahead, in plain words

Contracts first, so invalid combinations get caught before they reach a machine. Then a planner whose choices can be explained. Then fallback that behaves like a protocol instead of a hope. Then quantization whose quality is measured against a reference — or labeled, in plain text, “unmeasured.” Then a second backend, which is the real exam: if adding a GPU means changing the parts that talk to applications, the design was leaking all along. And last, the receipts and the ledger, so that anything an agent does inside this runtime can be answered for afterward.

One thin path, proved at every step, with the failures written down next to the successes. If you’ve read the rest of this Institute’s record, that method will sound familiar. It’s the same institute, pointed at a different environment: not the world a model learns in, but the machine it wakes up on.

Addendum · 17 November 2026

The build has since run to Phase 5, and the exam this guide was waiting for has been sat. The contracts, the planner, the fallback protocol, and a real trained model with measured quantization quality (Phases 1–4) are complete in the repository, each phase’s tests green and its evidence reproduced. Then the second backend arrived, and with it the question this page left open: if adding a GPU meant changing the parts that talk to applications, the design was leaking all along. It did not. Nothing above the backend line changed — checked mechanically, by diffing the tree against the Phase 4 commit — and on the Strix Halo, against criteria written down before the session ran, Phase 5’s verdict is PASS: the suite green with the GPU tests running, every protected file byte-identical, the planner choosing each backend where the targets demanded it, and the two backends’ answers agreeing — exactly on the demonstration model, to within a millionth on the flower classifier, labels exact everywhere.

The road there earned its own entries in the record, in this Institute’s usual way. The machine’s PyTorch build crashed inside its own bundled runtime on the first dispatched kernel — an environment finding, isolated by controlled diagnosis, and answered with a working build in an isolated corner of the machine. The session also exposed a flaw of the project’s own: discovery once probed for the GPU inside the runtime’s own process, so a backend that crashed on contact took the runtime down with it. The probe now runs in a disposable process of its own; a runtime that crashes on contact is simply reported absent, and the CPU serves on — demonstrated on the same broken installation that motivated it. The hardware runs caught two further bugs of ours, the same latent mistake in both the agreement test and the demonstration, of the kind that only exists because a test had never run anywhere before. First executions are exams too.

The proof now runs sixty tests; the precision evidence this guide quotes is unchanged to the last digit. What the layer still does not do is listed in the repository’s guide, which is kept current: nothing larger than a flower classifier, no measured-instead-of-estimated costs yet, no arbitration between agents. One further note belongs to the machine rather than the layer: the Strix’s NPU has been enabled and its compiler verified, as a track of its own. No backend speaks to it yet, and this record will not pretend otherwise.

Addendum · 18 November 2026

Phase 7 has been built: execution receipts. The layer now answers a question the phases before it could not. An agent working inside a runtime like this one reports that a task completed successfully — but how would anyone else know? Phase 7’s answer is three artifacts and a rule. A contract declares the computation before it runs: the operation, the authorized inputs, the exact result required. A receipt records what the execution system reports happened, bound by cryptographic hashes to the contract, its inputs, its output, and the program file supplied. And an independent verifier checks the evidence without trusting the executor’s assertion that it succeeded — it recomputes the result itself, from the contract, with its own arithmetic.

It was built three times, and the record keeps all three. Two independent first implementations agreed on the shape and differed in instructive places. Binding the receipt to the program artifact added a second trust anchor. Then a semantics audit of our own verdicts found a defect worth naming: a mathematically correct result was being failed when the program file differed from the trusted one — two different findings blurred into one verdict. The final architecture separates them, under three decisions written down and locked before it was built: the verifier never shares the executor’s arithmetic; a contract whose inputs would overflow its declared number range is rejected before execution, never silently wrapped; and every dimension of the evidence — contract, computation, artifact, provenance — is reported as its own finding, under a fail-closed rule that missing evidence can never pass.

The validation ran the way this Institute runs things. Twenty-three tests, including adversarial ones: output tampered with, program altered, contract substituted, anchors withheld. A receipt rewritten to claim it ran on the machine’s neural processor, attestation “claimed-valid,” verifies exactly like the honest one — because the claims are not evidence, and the verifier does not read them as evidence. The demonstration’s evidence files came out byte-identical on two different machines. And one line appears in every verification report the system produces, including the passing ones: execution provenance, INDETERMINATE. Hashes establish that recorded artifacts are intact and that a result agrees with its contract. They do not establish where the computation physically ran, or on what, and this record will not pretend otherwise — the layer’s own summary of itself is that it is an experimental system for independently evaluating whether computational results and supplied execution artifacts satisfy explicitly declared contracts, while distinguishing verified evidence from unsupported execution claims.

The package is public in the repository, standard library only, one command to run: github.com/salvajek356-sys/aacl/phase7. The specification it implements was frozen before the final build, and the decisions and the full dated record are published with it. What it does not do: authenticate physical execution, sign anything, or arbitrate between parties. Those are defined in the specification and unbuilt, and they will be reported the same way when they are attempted — either as done, or as not done.

Records.
